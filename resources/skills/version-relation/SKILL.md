# 版本关系候选与解释 Skill

## 目标

根据确定性比较节点已经产生的结构相似度、内容相似度、关键修改、有界差异证据、排序信号和关系约束，解释候选文件之间的版本关系，提出受控关系候选，并完成可复核的业务语义分类。

## 执行规则

1. 确定性比较结果和 `relation_constraints` 是事实与硬约束来源，不重新计算相似度，也不直接改变版本图。
2. 关系候选只能使用 `direct_revision`、`parallel_branch`、`derived_export`、`semantic_duplicate`、`unrelated` 或 `uncertain`。
3. 优先解释文件名版本号、修改时间、关键字段变化和结构增删如何共同支持或反驳现有判断。
4. 信号冲突或证据不足时输出 `uncertain`，不把推测写成事实。
5. 分叉、重复和派生关系必须区分说明，不把所有差异都描述为线性升级。
6. `relation_assessment.evidence_refs` 只能来自当前输入 `relation_evidence`，非 `uncertain` 候选至少引用一项。
7. 语义分类只能使用输出 Schema 定义的 `change_type`，每项必须给出重要性、旧值、新值、业务影响、证据引用和置信度。
8. 语义分类的 `evidence_refs` 只能来自当前输入 `change_evidence`；没有差异证据时不得生成语义分类。
9. 不输出“自动批准”“删除”“发送”“建立版本边”等动作，也不直接决定人工审核优先级；关系融合和审核动作由后续规则引擎计算。
10. 版本方向未知时不得猜测旧值和新值，也不得提出需要父子方向但不满足约束的关系。

## 输出检查

- 摘要必须覆盖至少一个关键修改或排序信号。
- 关系候选必须逐项满足输入中的哈希、父子、导出、重复、分支和无关文件约束。
- 付款期限、金额、责任主体、交付范围和违约责任等业务变化要与纯措辞、格式变化明确区分。
- 不虚构用户确认、发送记录或 PDF 来源证据。
- 不修改确定性节点生成的相似度和约束，不输出最终版本边。
